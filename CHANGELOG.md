# Changelog

All notable changes to this kit are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow [Semantic Versioning](https://semver.org/).

For organisations that have validated a tool with the kit: a new kit version is not automatically a change to your validation. A change to `admission/tasks/` or to the acceptance criteria is a change to the admission suite, so assess it under your change control before you use it for model admissions.

## Unreleased

## 0.2.0 - 2026-10-19

Two validation profiles, lite and full, in the same repository, distinct document IDs for lite, a style and messaging pass, plus the changes from the regulatory, practitioner and de-identification review of 0.1.0. Organisations that validated with 0.1.0: the admission suite changed (task `guardrail-denied-command` version 2, runner flags), so treat the new suite version as a plan change. Existing configs keep rendering the full profile (see Changed).

### Added

- Two validation profiles from the same config and variables. `full` is the in-depth package (the 0.1.0 content with the changes listed under Changed). `lite` is the risk-proportionate minimum for teams where AI output is always independently verified downstream (human review + CI): per tool `01-validation-plan`, `02-test-record` (IQ-03, OQ-01 to OQ-10, MA-01, PQ-01, PQ-02 in 12 records) and `03-validation-report` (document IDs `...-L01` to `...-L03`), plus a shared work instruction and tool-discovery checklist (`...-GEN-L01`, `...-GEN-L02`). Lite uses the REQ, IQ, OQ, MA and PQ IDs and the commands of full, with criteria equal to or stricter than full under each shared ID, so its evidence is reused when a team moves to full. The lite plan records L1 to L9 (when lite is not enough), the tool's known guardrail limitations, deviation classes, an interim-use look-back and a readiness checklist; the report has the trigger list and an admission record. Hard stops (pinned model policy, `agents_qms` or an agent write path to QMS systems outside the code-host gate, AI output used as evidence without review, an agent with secrets reading untrusted content) make `render` refuse lite unless `--force`, which marks the documents NOT VALID FOR RELEASE; `doc_drafting` and GxP give a prominent warning.
- `--profile lite|full` on `init` (stored in the config) and `render` (overrides the config); config key `profile`; optional config keys `agent_qms_write`, `ai_output_as_evidence`, `agent_untrusted_with_secrets`; template variables `profile`, `profile_lite`, `profile_full`, `full_recommended`, `full_reasons`, `lite_blocked`, `lite_blockers`, `config_file`, `owner_is_executor`. The wizard asks the hard-stop questions and then the profile, and recommends one from the answers. `render --force` overrides a hard stop and the refusal to write into a directory holding the other profile's documents.
- Tests for both profiles: the template matrix renders `templates/full/` and `templates/lite/` (no skips), and `tests/test_lite.py` checks the lite file set, the ID subset, the lite tests, the requirement subset, the full-profile warning, the hard stops, the documented differences under shared IDs and the word budget (default config: at most 5,000 words per lite per-tool package, 1,200 per lite shared document).
- Lite document IDs that never repeat a full-profile ID: per tool `L01` to `L03` (for example `ACME-VAL-CLAUDE-L01`, never the full inventory `ACME-VAL-CLAUDE-01`), shared `GEN-L01` and `GEN-L02` (never the full `GEN-01`, `GEN-02`), so one ID always names one document under document control (`kit/config.py` `derive()`, profile-aware). On upgrade the full documents supersede the lite records under their own IDs, the lite documents stay effective until the full release, the evidence IDs (IQ, OQ, MA, PQ) and paths are reused, and new deviations continue the lite numbering (`docs/lite-vs-full.md`, upgrade path). `L` plus two digits avoids confusion with the triggers L1 to L9.
- Messaging: README opens with "Why it matters" (tools that write or change product code, tests or quality records have a direct impact on quality; ISO 13485:2016 clause 4.1.6) and "No shadow AI" (undeclared tools, personal accounts and unlabelled AI-assisted changes cannot be validated, controlled or defended in an audit); a condensed version in `GUIDE.md` "Why now". The work instruction of both profiles has an explicit "No shadow AI" rule (only declared, organisation-approved tools and accounts; every AI-assisted change labelled; unknown tools reported; no AI tool on a personal account for company development or QMS work), and the tool-discovery checklists name shadow AI as what they look for.
- `tests/test_style.py`: no section sign in any tracked text file or rendered default package; no times or durations in README.md; no effort or speed claims in GUIDE.md and `docs/`; the shadow-AI message in README and GUIDE and the rule in both work instructions; GUIDE.md within 1,250 words; no lite and full document ID collision for the default config.
- `docs/lite-vs-full.md`: comparison of the profiles, the conditions L1 to L9 that require full with their anchors (ISO 13485:2016 clauses 4.1.6 and 7.3.6, IEC 62304, FDA CSA "high process risk", GAMP 5 appendices D9 and D11, EU GMP draft Annex 22), what lite leaves out and the residual risk it accepts, the differences under shared IDs, the upgrade path from lite to full with the same evidence IDs, and why a downgrade after release needs a documented change.
- Fictional filled lite example `examples/acme-medsoft-lite/` (Claude Code and OpenAI Codex, envelope policy, already in use, one major deviation corrected before release); `tests/test_examples.py` checks both examples (banner, rendered file set, no leftover template syntax or placeholders, nonconformity reference, and for lite the profile decision). `examples/acme-medsoft/` stays the full-profile example.
- Shared record `00-shared/code-host-gate-qualification.md` (`doc_id_gates`): the code-host gates (OQ-01 to OQ-07, OQ-12) are qualified once per code host for all tools, with per-step records, an evidence index under `evidence/GEN/` and the results credited to each tool.
- `checks/soup_gate.py` (required CI check against unapproved or non-existent dependencies, OQ-07 b) with `examples/github-workflow-soup-gate.yml` and `examples/github/approved-components.example.json`.
- `checks/mirror_protection.py`: copies branch protection, rulesets and the Actions approval setting to a sandbox repository and compares them.
- `checks/client_regression.py` with probe examples in `tools/claude-code/` and `tools/codex/`: automated client regression (CS-3a) as the gate for batched version raises and a security-fix fast path (T7a).
- OQ-13 (vendor change monitoring), RV-01 (retrospective review of use before validation, separate from PQ), a PQ-02 severity table, PQ-01 outlier rule, and an "approved with conditions" path until the PQ addendum.
- `examples/github/pull_request_template.md`, `examples/github/CODEOWNERS.example`, `examples/github-workflow-label-check.yml`.

### Changed

- README restructured around the two profiles (comparison right after the introduction, `--profile` in the quick start, both output layouts); `GUIDE.md` adds "Start lite, go in-depth when needed"; README_DEV documents the template directories and the profile variables.
- Kit and script version 0.2.0 (`kit/__init__.py`, `SCRIPT_VERSION` of every script, `run_canary.sh`); evidence files record it.
- Templates moved from `templates/` to `templates/full/`; lite templates live in `templates/lite/`. `--templates DIR` accepts a profile directory or a copy of `templates/` with `lite/` and `full/` subdirectories.
- New configs default to the lite profile (`init --defaults` writes `"profile": "lite"`). A config without the `profile` key (written by kit 0.1.0) still renders as full, with a notice. `render` lists Markdown files in the output directory that it did not write (for example the other profile's), so render each profile into its own directory.
- Every evidence script records who ran it (`--operator` or `$KIT_OPERATOR`, operating-system user, host, SHA-256 of the machine id, and the GitHub login where relevant), including `find_ai_footprint.py`. `check_github_gates.py --commits-since` matches every commit on the protected branch to a merged PR (look-back for interim use); `run_admission.py --list` prints the suite SHA-256 so the plan can fix it before execution.
- Validation plan: objective pre-authorised scope for Tier 2 changes with an enforced allow-list of admitted exact model ids, time-boxed admission after detection for tools without an enforced allow-list, re-test validity rules, MA-01 run-count rationale, isolation and denied-command control per tool, interim use with a mandatory nonconformity and CAPA reference, a preparation step before execution.
- Validated versions are the versions actually tested; the Claude Code example pins `requiredMinimumVersion` and `requiredMaximumVersion` to the tested version.
- `check_github_gates.py`: required checks verified on merged PRs (check runs and statuses), retention setting recorded and expired results reported as inconclusive, launcher of agent-authored PRs excluded from qualifying approvals with a compensating control.
- `run_canary.sh`: server-side merge attempt through the REST API with HTTP status, admin and merge-queue detection, preconditions for OQ-07 variants, result `pass` / `fail` / `inconclusive`.
- `capture_baseline.py`: Claude Code managed sources evaluated in the client's own order and merge behaviour, findings name their source, graded `--compare` with `--approved-version`.
- `run_admission.py`: isolation from the executor's user configuration, denied-command control (`--deny-control`, N/A with a reason where no control exists), check of the model actually used (`--aux-model`, `--model-log`), baseline variants.
- Claude Code example: secrets denied, gate files asked instead of denied, mods restricted with `allowManagedModsOnly` and `disableSideloadFlags` (`allowManagedHooksOnly` recommended for runners), realistic domain list, exact model matching, static attribution. Codex examples: `inherit = "all"` with explicit filters, `cli_auth_credentials_store = "auto"`, MCP allowlist shipped commented out.
- 21 CFR Part 11 and ISO 13485 clause 6.2 c) mapped where they apply; audit-finding lists reworded as design rules of the kit.
- Style: clauses and sections are cited without the section sign everywhere (templates of both profiles, examples, docs, tool notes, wizard labels): "ISO 13485:2016 clause 4.1.6", "IEC 62304 clauses 5.1.10 and 8.1", "21 CFR 820.10", "21 CFR 11.10(e)", "MDR Article 10(8)", "AI Act Article 4", "section 5 of `04`".
- Style: README.md states no times or durations; GUIDE.md and `docs/` make no effort or speed claims (the worked example of `docs/model-change-protocol.md` uses steps instead of clock times and no effort total; the schedule of the full validation plan uses named steps instead of Day 0 to Day 5; the three tiers of the model change protocol are named by what they run, not by effort labels, in `docs/` and the full plan and change documents). Minimum observation periods and review cadences that are acceptance criteria stay. `GUIDE.md` shortened to stay within 1,250 words.
- Defaults use obviously fictional placeholders (organisation "Acme MedSoft", model envelope `anthropic-model-*` / `openai-model-*`); the de-identification deny-list moved out of the repository.

## 0.1.0 - 2026-10-18

First public release.

### Added

- `kit.py` CLI (`init`, `render`, `example-config`, `vars`) with an interactive wizard, a strict mustache-like template engine (standard library only) and optional `.docx` output through pandoc.
- Document templates: a shared work instruction and tool-discovery checklist, and per tool the inventory and intended use, requirements REQ-01 to REQ-17, risk assessment, validation plan with the three-tier model change protocol, test protocol (IQ-01 to IQ-05, OQ-01 to OQ-12, OQ-20, OQ-30, OQ-40, MA-01, PQ-01, PQ-02), configuration baseline, validation report and change and revalidation.
- Options for risk model (CSA or three-level), contexts of use, surfaces, code host, model policy (envelope or pinned), GxP, and retrospective validation when the tool is already in use.
- Evidence scripts in `checks/`: GitHub gate check, configuration baseline capture, AI footprint scan, canary PR.
- Model admission suite in `admission/`: runner, vendor-neutral JSON tasks and fixtures.
- Tool notes and verified configuration examples for Claude Code (`tools/claude-code/`) and OpenAI Codex (`tools/codex/`).
- Documentation: `GUIDE.md`, `docs/regulatory-mapping.md`, `docs/model-change-protocol.md`, `docs/adapting-other-tools.md`.
- Fictional filled example (`examples/acme-medsoft/`) and a workflow example for exporting review evidence.
- Unit tests and GitHub Actions CI.

Vendor facts verified on 2026-10-18 (Claude Code v2.1.302, Codex CLI 0.163.0).
